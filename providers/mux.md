# Mux — default provider, church-owned account

The integration uses the congregation's own Mux environment. The church pays Mux directly, can disconnect at any time, and can play verified local recordings after disconnecting. The component ships no shared Mux credentials. Mux documents a comparable church-software deployment in its [Omnia case study](https://www.mux.com/case-studies/omnia). Mux's [OSS programme](https://www.mux.com/oss) lists a PHP SDK and optional contributor awards; budget production under the church's [account plan](https://www.mux.com/pricing).

## Connect and adopt

1. Choose production or test explicitly. Store the environment token ID and secret server-side. The Video API uses HTTP Basic authentication over TLS. Read access supports discovery; request Video write access only for creating/updating inputs or renditions. Signing keys for restricted playback, webhook signing secrets, and stream keys are separate credentials.
2. List live streams in the selected environment, including paginated results. Display label, masked identity, playback policy, current state and whether already bound locally. Let the operator adopt an existing stream without resetting its key. For a new one use POST /video/v1/live-streams and record the returned live-stream ID and playback IDs. Select the live playback policy and new_asset_settings recording playback policy independently. Default to restricted exposure when church access requires it.
3. Expose the encoder's RTMPS server and its own stream key only to authorized volunteers. A new rotation uses the explicit reset-stream-key operation and can interrupt an existing setup; require operator action and show which encoder must be updated. Normal account tests perform reads. The playback client receives only permitted playback data.
4. Configure the webhook endpoint in the same Mux environment, verify its signature, and test incoming events against the connection. If the church cannot expose an inbound endpoint, use scheduled read-only reconciliation. On shared hosting without a reliable task runner, identify this limitation in the connection health panel.
5. Select service attribution and archive policy. One reusable live stream per church/channel is convenient for weekly use. Allocate distinct live streams for overlapping rooms or independent languages. A single persistent stream key cannot identify which preacher is speaking.

## Resource and action mapping

| Purpose | API/resource | Mapping |
| --- | --- | --- |
| Discover or reconcile | GET /video/v1/live-streams and GET /video/v1/live-streams/{id} | Save live-stream ID as channel identity. An active_asset_id, where present, identifies this recording. Historical asset IDs are different from current live playback IDs. |
| Create or change configuration | POST /video/v1/live-streams; PATCH /video/v1/live-streams/{id} | Record returned playback_ids and effective policy. Apply capability-aware field changes. Read after timeouts. Never recreate an input merely to edit next Sunday's local title. |
| Live player | https://stream.mux.com/{PLAYBACK_ID}.m3u8 or Mux Player | Use native church player with HLS when desired. Signed policy needs a server-generated short-lived playback JWT scoped to the correct playback ID/audience; do not send signing private keys to Joomla frontend. |
| Calendar/countdown | Local programme and occurrences | The live-stream resource represents an encoder destination. Joomla owns the church calendar/countdown; a reusable input's idle state carries no scheduled event time. No fake remote event for every Sunday. |
| Confirm live | Verified video.live_stream.active or reconciled active stream | Connected means the encoder connected; active means playable. Associate the active recording and start time with precisely one occurrence. Avoid assigning a rehearsal. |
| End/reconnect | Disconnected, idle, asset events; read back when necessary | Keep a disconnect transient through the configured reconnect window. Idle ends the active live session. Check the asset separately for recording readiness. Reversal of delivery order never ends a newer occurrence. |
| Recording | GET /video/v1/assets/{asset_id}; live recordings have their own asset and playback identity | Record live_stream_id and the asset-to-session mapping. Asset ready may occur before the live broadcast has ended. Require finalized live recording and the requested export before completing local archival. |
| Local video/audio | Create asset static renditions with resolution highest for MP4, audio-only for M4A; or explicitly request temporary master access | Wait for video.asset.static_rendition.ready or read per-file status. Use the returned rendition name and correct policy/token; highest can be skipped for audio-only input and audio-only can be skipped for video-only. Report missing tracks. |
| Backup-quality master | PUT /video/v1/assets/{id}/master-access with temporary access | Master download URL expires after 24 hours. Authorize and fetch privately, refresh if it expires. Master is for backup/editing; generate or verify a browser-compatible local playback file. |

## Event flow

Process webhook message id once per environment. Validate Mux-Signature against the raw request and signature timestamp using the official scheme, before parsing or mutating. Store the event ID, resource IDs and occurred time. Use video.live_stream.connected/active/disconnected/idle for signal transitions and video.asset.live_stream_completed for the end of the live asset where delivered. Observe video.asset.ready, video.asset.errored, static rendition and master-ready signals separately. On missing, duplicate or out-of-order callbacks, read both the stable live stream and the specific recording asset. Do not use the new week's active asset to resolve last week's export.

For members-only services, choose a signed policy for both live and replay, issue audience-limited tokens only after Joomla access checks, and refresh during long services. A public playback ID saved earlier remains public independently of Joomla's menu. Review other public playback IDs on an adopted resource before claiming member-only enforcement.

## Sunday acceptance

Start with an already configured OBS key and a published Sunday occurrence. Viewers see a countdown. Start encoding early in rehearsal mode, then associate the actual service. At active, the preacher page shows Watch live. Disconnect briefly and reconnect inside the configured window; preserve the original occurrence. Stop, receive the completed asset, generate both renditions, deliver audio first and video twice. Expect one sermon, one audio and one video. Select local replay and disconnect the provider; both files still play under the sermon ACL. Repeat with a signed channel, an expired master URL, an asset missing audio, and an unrelated active stream from another church.
