# Extend the Sermon Distributor blueprint

## Source hierarchy and baseline

Use the package supplied for the implementation run as the maintained source. Record its checksum/revision, component definition GUID, package format, target Joomla/PHP/JCB versions, enabled plugins, configured repositories and dependency versions in that run's handoff. This is an upgrade to the same extension. Preserve component identity, existing business data, languages and public links. Compile the unmodified package once and retain a reference installation with an existing sermon, preacher, church, file and menu.

Two kinds of product evidence inform this specification:

| Evidence | What it establishes | Application |
| --- | --- | --- |
| Public compiled Joomla component, revision c8a6ec9c3f9e06a206fa0d2e40a38c2a5e973dff | Version 6.0.0 manifest; administrator schema, church/preacher selectors and managed Files implementation | Locate the corresponding native definitions in the incoming package. Generated output provides a comparison target. |
| Seven supplied site-view dumps, Categories, Preachers, Category, Preacher, Sermon, Series and SeriesList | Rendered items/lists have numeric IDs, GUIDs and composed links. The sermon uses preacher, series and category GUIDs. Its projection can include download_links, viewKey and playerKey. | Preserve those view contracts. A rendered property may come from a join, getter or presentation step. Never infer a database column or decode a legacy download URL from a dump. |
| JoomEngine skills, revision da117faab903a777fab98a012464ef9238e19869 | Native model ownership, package identity, reuse, routing, storage and validation procedures | Use the current compatible production toolchain when building. The cited revision makes the research reproducible. |

The inspected public tree has administrator and API sections; it does not contain the site templates seen in the samples. The supplied package may be more advanced. Inventory both surfaces before editing. Never import real contacts, local paths, signed URLs or sample tokens into fixtures or documentation.

## Map existing application data

| Native owner | Observed contract | How streaming consumes it |
| --- | --- | --- |
| Sermon Admin View | sermon.guid, name, alias, church, preacher, category, series, published and access | Use the normal model save and authoring workflow. Name is required in the observed form. Fill the actual required fields of the incoming package. Preserve its alias collision rules and access asset. |
| Preacher Admin View | preacher.guid identifies the person; preacher.church associates a church | Select an existing preacher by GUID. A guest can preach for another church. The scheduled host church is a separate explicit choice. Never reassign the preacher's home church while archiving. |
| Church Admin View | church.guid and numeric id, published, access | Resolve connection ownership, calendar filter and sermon.church to this record. A Joomla site can host multiple churches. Never infer the owner from the first row or domain. |
| Category, Series | Existing selectors carry row GUIDs | Optional series/category defaults may come from a programme, and an occurrence can override them. No synthetic taxonomy for live content. |
| Files and File Types | file.entity + entity_type identify owner; file_type is a type GUID; file.guid identifies the attachment; access, file_path, extension, mime, size have distinct owners | Associate verified local media with the sermon GUID and existing sermon target string. Reuse allowed targets, media formats, paths, quantity and download rules. A provider asset ID is not a File GUID. |
| Site views and routers | Dumps expose preacher/sermon links and linked items in list/detail pages | Add a live section to the actual Preacher Site View. Preserve its existing query, layout, filters, player and SEF routes. The new status link uses the church occurrence route. |

The public File Manager's upload method expects a file type GUID, owning entity GUID and target and obtains an upload from its agent. Its definition/download logic evaluates access; its quantity limiter can delete old files with the same entity/type/target. Do not simulate a browser upload or assume an unattended file can be passed to that method. Trace the actual manager, model and file-definition owner. Reuse the final validated persistence operation, or extend the native Power with a staged-file entry point sharing the same checks. Reserve a compatible file type for each retained format when quantity rules would otherwise evict an existing attachment. Test a legacy attachment plus a new audio and video before enabling automation.

## Working order for the implementation agent

1. Open the supplied package in an isolated JCB authoring instance. Identify its package/import route and dependencies. Preserve any encrypted-package requirements outside version control. Check the dependencies resolved to the selected repositories in their intended order.
2. Trace the existing Sermon save, Preacher page, Church selector, File/File Type manager, access policy, site routing and scheduler hooks. Inventory any countdown or calendar feature already present. Record definition GUID, owning record, file/field or hook, current callers, GUI location and installed outcome. If an existing timer supports recurrence, reuse its owner and adapt display/status transitions; retain its old timers and menu parameters.
3. Keep existing entity and definition identities. Numeric database IDs support Joomla CRUD; GUIDs join portable business rows; JCB definition identities identify blueprint records; provider resource IDs are opaque strings scoped to a connection. Importing reference definitions requires their complete dependency graph. Use native GUID modal selectors and filtered fields as in Sermon.
4. Implement persisted new entities from [the data contract](data-contract.md) through Fields, Admin Views and component association records. Where a related editor uses a normalized subform, attach its child Admin View and its real load/save path. Add indexes/uniqueness through the target compiler's supported schema/update mechanism. Verify the installed schema on both clean install and upgrade.
5. Attach Site Views for live service and calendar, supported menu item types and route registration. Use Dynamic Gets for visible occurrences, preacher live badges and lists. Keep provider network IO out of a page query. Share countdown, live state, source chooser and replay fragments through Layouts/Templates. Author the positionable countdown/list module **in JCB**. Route links with the component router and active Joomla menu/language context.
6. Place provider-specific authentication and resource translation in cohesive Super Powers injected through the component's service provider. The Joomla-native entry points for admin actions, callbacks, tasks and console commands delegate to these services. Look first at core APIs, then the central Super Power and Joomla Power indexes. Resolve the real SPK/JPK from the selected catalogue and its dependencies; reference the discovered keys in JCB source. Keep SDKs as declared dependencies/assets with their licenses. Confine their types to the adapter. Use the PHP SDK for Mux when compatible with the package's PHP/dependency policy.
7. Compile and install with JCB. Inspect public/private media delivery, allowed iframe hosts, language strings, request token handling, task enablement and generated menu metadata. Test using the real server entry points. A local-only Playground can validate views, recurrence and a simulated callback; inbound internet webhooks, long-running media jobs and production DNS require a reachable authorized test environment.
8. Correct defects in the blueprint and regenerate. Export the complete changed source graph plus the installable extension when an implementation is assigned. Reimport into a clean second instance and compile again. Do not fix a generated PHP file as the maintained solution. Keep deployment or provider writes confined to the designated test tenant.
