# Delivery sequence and verification gates

The requested change in this repository is documentation. The sequence below is for the agent who receives the source blueprint and authorization to implement. Each increment has an installed result the church can exercise. A generic link mode is a real deliverable for link-only platforms; built-in Mux automation and provider-supported scheduling/archival are separate required outcomes.

| Increment | Author in JCB | Completion evidence |
| --- | --- | --- |
| Baseline | Import existing package and dependency closure, compile its current consumer before changes | Equality of existing preacher, sermon, file access, menu, download and SEF behaviour on seeded data |
| Native entities and public views | Connection, programme/occurrence, destination, mappings; basic local recurrence, public views, approved player/link and menu/module wiring | No provider credentials needed to show a correctly authorized Wednesday/Friday/Sunday calendar and external service page |
| Default Mux | Account discovery/adoption, selected provisioning, safe player, signed events, reconciliation and one-session binding | A test-account broadcast changes the right preacher's state and produces an independently identified recording |
| Local archive | File staging/verification, authorized exports, editorial inbox, exactly-once sermon association, replay preferences | Both audio and video attach to one existing-model sermon; local replay remains after disconnection |
| Provider schedule integration | YouTube as dated broadcast reference case; adopt/disambiguate, write single events, re-read revisions; Vimeo/PeerTube/Twitch/Restream/Telegram/Meta/meetings according to profile | A supported upstream change is entered once and appears in Joomla or at the provider, including exceptions and conflict cases |
| Additional playback and archive integrations | Cloudflare, IVS and the remaining provider matrix, source priority, external handoff, permitted archive routes and capability discovery | Each row's default/fallback/forbidden path passes the provider test plan; gated operations accurately reflect account entitlements |
| Hosting and recovery | Task/CLI registration, file transfer restarts, reconciliation, optional capture, links/privacy/accessibility and diagnostics | Server interruption, duplicate events, low disk, private sources and limited shared hosting each have a tested recoverable outcome |
| Upgrade and release | Attach full graph; verify native migrations and rebuilt artifacts | Reinstall previous version with data, upgrade, rebuild twice, import/export to second JCB instance, publish evidence and runnable package per assignment |

## Configuration and deployment decisions at implementation time

Record the actual target versions from the provided package and the church's host. Select a maintained recurrence library or pre-existing countdown owner and compare it against the explicit scheduling examples. Pick only media player assets that support the required formats and browser policy. Identify license, local bundling, pinning, update and fallback for each SDK/player. Inventory the PHP extensions needed for outbound HTTPS, secure randomness, JSON, storage and any chosen optional processing. Advertise optional capture/conversion only when the host passes a read-only capability check. The common live player/calendar experience has no dependency on FFmpeg, a resident worker or a church VPS.

Use separate test accounts/environments; distinguish a provider account test stream from a public real-world church service. Test publication, paid operations and destructive deletion only with disposable resources provisioned for that purpose. Keep redacted evidence of recording completion, downloaded track and local seek. A mocked provider profile tests local idempotency; it cannot certify expiring upstream fields, geographic access, privacy or API eligibility.

## Agent acceptance deliverables

* Reproducible JCB package/export and compiled installable output, with definition/association identities and license records for any dependencies.
* Before/after evidence for existing sermon/preacher routes and download/authorization behaviour, including previously saved data and menu aliases.
* One real end-to-end owned Mux environment where granted, or an explicit recorded limitation when that tenant is unavailable; separate proof of a scheduled-event provider and an external-button provider. Keep vendor/account-dependent test outcomes separate per provider.
* Redacted data showing one occurrence, multiple outputs, exactly one sermon, church/preacher links and verified audio/video file associations. Include the case where provider files are unavailable but the church supplies its original.
* Recording of the operator workflow from first-run connect to weekly service, substitute preacher, local replay and disconnect. Verify the font/controls, contrast, focus order, captions and mobile playback under the actual installed template.
* Runbook for the hosting operator: endpoint and callback diagnostics, scheduler activation, transfer limits, backup/restore, domain changes, token rotation and moving a church to a new provider. This must match the generated product.

## Rollout controls

A new install or upgrade leaves integrations unconnected until the church opts in. Existing sermons, files and menus remain functional without live configuration. Enable scheduled writes only once per production installation identity. In rehearsal, keep provider mutations off or bound to test accounts. Rollback of the feature disables jobs and menu placements without destroying source media or historic sermon rows; schema rollback involving real data requires the site's backup/restore procedure. Report any outstanding upstream ownership, quota, regional or host limitations in the installed administration view.
